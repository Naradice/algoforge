## Running locally (dev)

### Prerequisites
- PostgreSQL 16 running at `localhost:5432` (db: `algoforge`, user: `algoforge`, password: `algoforge`)
- Redis 7 running at `localhost:6379`
- Python 3.12 venv with `pip install -r backend/requirements.txt`
- Node 18+ with `npm install` in `web/`

### Start the stack (multiple terminals)

```bash
# Terminal 1 — API server (auto-reloads on file save)
cd backend
uvicorn main:app --reload --port 8000

# Terminal 2 — collection worker (heavy disk I/O, 3 parallel processes)
cd backend
celery -A celery_worker worker -Q collection -c 3 --loglevel=info

# Terminal 3 — characteristics worker (fast, high concurrency)
cd backend
celery -A celery_worker worker -Q characteristics -c 12 --loglevel=info

# Terminal 4 — training + backtest workers
cd backend
celery -A celery_worker worker -Q training,backtest -c 2 --loglevel=info

# Terminal 5 — Next.js dev server
cd web
npm run dev
```

> **Windows note:** The `prefork` pool uses shared memory (`mmap` via billiard) which
> requires elevated access on Windows. Use `--pool=solo` instead for local dev:
> ```bash
> celery -A celery_worker worker -Q collection,characteristics,training,backtest --pool=solo --loglevel=info
> ```
> `solo` runs tasks in the worker's main process — no child processes, no permission issues.
> Process isolation is fully restored when running under Docker (Linux) in production.

For quick local dev you can run all queues in a single worker:
```bash
cd backend
# Linux / Docker:
celery -A celery_worker worker -Q collection,characteristics,training,backtest -c 4 --loglevel=info
# Windows (local dev):
celery -A celery_worker worker -Q collection,characteristics,training,backtest --pool=solo --loglevel=info
```

- UI:       http://localhost:3000
- API docs: http://localhost:8000/docs
- MCP:      http://localhost:8000/mcp (SSE transport)

### Full stack via Docker
```bash
cd infra
cp .env.example .env   # set GOOGLE_API_KEY at minimum
docker compose up --build
```

## Database migrations

```bash
cd backend

alembic revision --autogenerate -m "description"   # generate new migration
```

Migration files live in `backend/alembic/versions/`. Always review autogenerated files before committing — autogenerate misses some SQLAlchemy constructs (e.g. JSONB defaults).

## Testing

### Quick check — unit tests only (no DB/Redis needed)
```bash
cd backend
pytest tests/unit/ -v
```

### Full suite before a release
```bat
REM Windows — from algoforge/ root or scripts/
scripts\test-all.bat           # all three suites
scripts\test-all.bat unit      # backend unit only
scripts\test-all.bat frontend  # Jest only
```

### Backend (pytest)
```bash
cd backend
pytest tests/unit/                  # unit tests — mocked DB, fast (~1s)
pytest tests/ --ignore=tests/unit   # integration tests — requires live PostgreSQL
pytest tests/test_health.py -v      # single file
```

`asyncio_mode = auto` is set in `pytest.ini` — no `@pytest.mark.asyncio` needed.
Unit tests in `tests/unit/` mock the repository and never touch the database.
Integration tests use a real SQLite in-memory DB (configured in `conftest.py`).

### Frontend (Jest)
```bash
cd web
npm test                   # run once
npm run test:watch         # watch mode
```

Test files live in `web/__tests__/`. Component tests use React Testing Library.

### What to test after each area of change

| Changed area | Run |
|---|---|
| DDM simulator (`data/collectors/ddm_simulator.py`) | `pytest tests/unit/test_ddm_simulator.py -v` |
| Data service (`data/service.py`) | `pytest tests/unit/test_data_service.py tests/test_data.py -v` |
| Strategy engine | `pytest tests/unit/test_strategy_service.py tests/test_strategy.py -v` |
| Model layer | `pytest tests/unit/test_model_service.py tests/test_model.py -v` |
| API schema changes | `pytest tests/unit/test_schemas.py -v` |
| Frontend components | `npm test` in `web/` |
| Any backend router | `pytest tests/test_health.py tests/test_data.py -v` (smoke test) |

### Release checklist

Before merging a significant change:
1. `scripts\test-all.bat unit` must be green (fast, always required)
2. `scripts\test-all.bat` (full suite) should be green when possible
3. Manually verify the affected UI flow end-to-end in the browser
4. If a new datasource type or collector was added, run a real collection job and check the dataset appears in `/data`

## Maintaining documentation (`docs/`)

The `docs/` directory is the authoritative human-readable reference for the platform.

| File | What it covers |
|------|---------------|
| `README.md` | Index, architecture overview |
| `architecture.md` | Backend/frontend structure, key design decisions |
| `strategy-layer.md` | Strategy JSON schema, indicators, condition types, execution modes |
| `model-layer.md` | ML architectures, training lifecycle, deployment, inference |
| `data-layer.md` | Datasource types, collection flow, dataset characteristics |
| `mcp-guide.md` | All MCP tools, resources, example agent workflows |
| `roadmap.md` | Phased feature plan (Phase 1–5) |

**Rules:**
- When you add a new API endpoint, update the relevant layer doc and `mcp-guide.md` if it becomes an MCP tool.
- When the strategy execution schema changes (new condition type, new indicator), update `strategy-layer.md`.
- When a roadmap item is completed, move it to a "Done" section or remove the checkbox.
- Docs describe the *actual* implementation — never document planned features as if they exist.

## Maintenance scripts (`scripts/`)

| Script | Purpose |
|--------|---------|
| `test-all.bat` | Run the full test suite (backend unit + integration + frontend). Pass `unit`, `integration`, or `frontend` to run one suite. Exits non-zero on any failure — use as release gate. |
| `cleanup-data.bat` | Delete all datasources, datasets, collection jobs, strategies, and models via the API; remove artifact files. Run from the `scripts/` directory. Requires the API to be running. |
| `clear-stuck-jobs.bat` | Clear orphaned Celery task keys from Redis. Run when workers show tasks stuck in `STARTED` state after an ungraceful shutdown (Ctrl+C on Windows). |

To add a new script: create a `.bat` file in `scripts/`, add a row to this table.

## Key architectural rules

1. **Three-layer separation** — Data, ML Model, and Strategy layers communicate only through the HTTP API and shared artifact paths. No direct Python imports across layer boundaries.

2. **Response envelope** — All API responses use `{ "data": T, "meta": {...} }`. The frontend `fetcher` unwraps `.data`; use `fetcherWithMeta` when you need `meta.total` for pagination counts.

3. **Async jobs via Celery** — Long-running operations (collection, training, backtest) are enqueued to Redis by the HTTP endpoint (returns 202) and executed by Celery workers. Never run them synchronously in a router. Route tasks to the correct queue (`collection`, `characteristics`, `training`, `backtest`) so concurrency limits apply correctly.

4. **SSE streaming** — Running jobs publish events to the in-process `EventBus`. Frontend subscribes via `useSSE` hook. Strategy run events: `GET /strategies/{id}/runs/{run_id}/events`. Training events: `GET /training-runs/{run_id}/events`.

5. **Strategy definition format** — Stored as JSONB. The execution engine reads `indicators[]`, `entry`, `exit`, and `risk` at runtime. See `docs/strategy-layer.md` for the full schema.

6. **Toast notifications** — Use the `useToast()` hook (from `@/lib/toast`) for user feedback on async operations. Every mutation that calls an API should show a success or error toast.

7. **SWR polling** — Use `refreshInterval` smartly: poll fast while a job is active, slow (or zero) when idle. Pattern: `refreshInterval: (data) => data?.status === "running" ? 3000 : 0`.

## Common tasks

### Add a new datasource type
1. Create `backend/data/collectors/<type>.py` with `collect(datasource_id, config) → CollectResult`. Write output as partitioned parquet via `pyarrow.parquet.ParquetWriter` — never buffer the full dataset in memory.
2. Add dispatch in `backend/celery_worker.py` `run_collection_job()`
3. Add default config in `web/app/data/new/page.tsx` `TYPE_CONFIGS`
4. Update `docs/data-layer.md`

### Add a new strategy condition handler
1. Add handler in `backend/strategy/engine/conditions.py` `_eval_one()`
2. Add any required indicator in `backend/strategy/engine/indicators.py`
3. Update `docs/strategy-layer.md` and the example templates in `web/app/strategy/new/page.tsx`

### Add a new ML architecture
1. Add training logic in `backend/model/training.py`
2. Add inference logic in `backend/model/inference.py`
3. Add config schema to `GET /model-config/architectures/{architecture}` in `backend/model/config_router.py`
4. Update `docs/model-layer.md`

### Add a new MCP tool
1. Add the function to the appropriate file in `backend/mcp_server/tools/`
2. Update `docs/mcp-guide.md` with the tool signature and description
