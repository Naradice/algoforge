## Running locally (dev)

### Prerequisites
- PostgreSQL 16 running at `localhost:5432` (db: `algoforge`, user: `algoforge`, password: `algoforge`)
- Redis 7 running at `localhost:6379`
- Python 3.12 venv with `pip install -r backend/requirements.txt`
- Node 18+ with `npm install` in `web/`

### Start the stack (3 terminals)

```bash
# Terminal 1 — API server (auto-reloads on file save)
cd backend
uvicorn main:app --reload --port 8000

# Terminal 2 — background job worker (collection, training, backtest)
cd backend
python -m arq arq_worker.WorkerSettings

# Terminal 3 — Next.js dev server
cd web
npm run dev
```

- UI:       http://localhost:3000
- API docs: http://localhost:8000/docs
- MCP:      http://localhost:8000/mcp (SSE transport)

### Skip Redis (quick local dev)
Set `ALGOFORGE_NO_REDIS=1` in `backend/.env`. The event bus falls back to an in-process implementation; async jobs still run but SSE events won't cross processes.

### Full stack via Docker
```bash
cd infra
cp .env.example .env   # set GOOGLE_API_KEY at minimum
docker compose up --build
```

## Database migrations

```bash
cd backend
alembic upgrade head          # apply all pending migrations
alembic revision --autogenerate -m "description"   # generate new migration
```

Migration files live in `backend/alembic/versions/`. Always review autogenerated files before committing — autogenerate misses some SQLAlchemy constructs (e.g. JSONB defaults).

## Testing

### Backend (pytest)
```bash
cd backend
pytest tests/                       # all tests (requires live DB + Redis)
pytest tests/unit/                  # unit tests only (no DB required)
pytest tests/test_health.py -v      # single file
```

`asyncio_mode = auto` is set in `pytest.ini` — no `@pytest.mark.asyncio` needed.
Integration tests in `tests/` use a real database. Unit tests in `tests/unit/` mock the DB.

### Frontend (Jest)
```bash
cd web
npm test                   # run once
npm run test:watch         # watch mode
```

Test files live in `web/__tests__/`. Component tests use React Testing Library.

## Maintaining documentation (`docs/`)

The `docs/` directory is the authoritative human-readable reference for the platform.

| File | What it covers |
|------|---------------|
| `README.md` | Index, architecture overview |
| `architecture.md` | Backend/frontend structure, key design decisions |
| `strategy-layer.md` | Strategy JSON schema, indicators, condition types, execution modes |
| `model-layer.md` | ML architectures, training lifecycle, deployment, inference |
| `data-layer.md` | Datasource types, collection flow, dataset characteristics |
| `mcp-guide.md` | All MCP tools, resources, example agent workflows |
| `roadmap.md` | Phased feature plan (Phase 1–5) |

**Rules:**
- When you add a new API endpoint, update the relevant layer doc and `mcp-guide.md` if it becomes an MCP tool.
- When the strategy execution schema changes (new condition type, new indicator), update `strategy-layer.md`.
- When a roadmap item is completed, move it to a "Done" section or remove the checkbox.
- Docs describe the *actual* implementation — never document planned features as if they exist.

## Key architectural rules

1. **Three-layer separation** — Data, ML Model, and Strategy layers communicate only through the HTTP API and shared artifact paths. No direct Python imports across layer boundaries.

2. **Response envelope** — All API responses use `{ "data": T, "meta": {...} }`. The frontend `fetcher` unwraps `.data`; use `fetcherWithMeta` when you need `meta.total` for pagination counts.

3. **Async jobs via arq** — Long-running operations (collection, training, backtest) are enqueued to Redis by the HTTP endpoint (returns 202) and executed by the arq worker. Never run them synchronously in a router.

4. **SSE streaming** — Running jobs publish events to the in-process `EventBus`. Frontend subscribes via `useSSE` hook. Strategy run events: `GET /strategies/{id}/runs/{run_id}/events`. Training events: `GET /training-runs/{run_id}/events`.

5. **Strategy definition format** — Stored as JSONB. The execution engine reads `indicators[]`, `entry`, `exit`, and `risk` at runtime. See `docs/strategy-layer.md` for the full schema.

6. **Toast notifications** — Use the `useToast()` hook (from `@/lib/toast`) for user feedback on async operations. Every mutation that calls an API should show a success or error toast.

7. **SWR polling** — Use `refreshInterval` smartly: poll fast while a job is active, slow (or zero) when idle. Pattern: `refreshInterval: (data) => data?.status === "running" ? 3000 : 0`.

## Common tasks

### Add a new datasource type
1. Create `backend/data/collectors/<type>.py` with `collect(datasource_id, config) → CollectResult`
2. Add dispatch in `backend/arq_worker.py` `run_collection_job()`
3. Add default config in `web/app/data/new/page.tsx` `TYPE_CONFIGS`
4. Update `docs/data-layer.md`

### Add a new strategy condition handler
1. Add handler in `backend/strategy/engine/conditions.py` `_eval_one()`
2. Add any required indicator in `backend/strategy/engine/indicators.py`
3. Update `docs/strategy-layer.md` and the example templates in `web/app/strategy/new/page.tsx`

### Add a new ML architecture
1. Add training logic in `backend/model/training.py`
2. Add inference logic in `backend/model/inference.py`
3. Add config schema to `GET /model-config/architectures/{architecture}` in `backend/model/config_router.py`
4. Update `docs/model-layer.md`

### Add a new MCP tool
1. Add the function to the appropriate file in `backend/mcp_server/tools/`
2. Update `docs/mcp-guide.md` with the tool signature and description
