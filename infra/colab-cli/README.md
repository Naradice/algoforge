# colab-cli container

Runs [google-colab-cli](https://github.com/googlecolab/google-colab-cli) — a CLI that
provisions a real Colab runtime and drives it from the terminal — inside a container, since the
tool officially supports Linux/macOS only and this dev machine is Windows.

Independent of `../docker-compose.dev.yml` (algoforge's own backend/celery services) on purpose:
different `docker compose` project, own compose file, no shared network/volumes — starting,
stopping, or rebuilding this can never affect a training/collection job running in the main
stack.

## Setup

```
cd algoforge/infra/colab-cli
docker compose build
docker compose up -d
docker compose exec -it colab-cli colab status
```

There's no separate `colab auth` command — `--auth` (default `oauth2`) is a global option, and
any command run while unauthenticated triggers the login flow automatically. Confirmed in this
environment: running any command (e.g. `colab status`) unauthenticated prints a Google OAuth URL
and then waits with `Enter the authorization code:` — open that URL in a browser on this
machine, approve, and paste the code Google shows back into the terminal. Requires `-it` (a real
TTY) since it's a blocking prompt, not a one-shot flag.

The resulting token lands in the `colab_cli_config` volume (`~/.config/colab-cli/` inside the
container) and survives `docker compose down` / rebuilds — only `docker compose down -v` or
`docker volume rm colab-cli_colab_cli_config` clears it.

If `oauth2` turns out to be inconvenient for repeat use, `--auth adc` (Application Default
Credentials, e.g. pointing `GOOGLE_APPLICATION_CREDENTIALS` at a service account key — no
browser needed) is the alternative, passed the same way: `colab --auth adc status`. Not yet
tried against Colab specifically — unconfirmed whether Colab compute quota can be granted to a
service account at all (Colab is normally tied to a personal Google account's own quota).

## Usage

**`colab run` is for standalone `.py` scripts only — it does not take `.ipynb`.** Notebooks run
via `colab exec -f`, against a session created with `colab new` (confirmed from `colab readme`'s
bundled docs, not guessed). Notebooks generated by `backend/scripts/generate_colab_notebook.py`
(default output dir `algoforge/notebooks/`) are mounted read-write at `/notebooks`:

```
docker compose exec colab-cli colab new -s tiny-lstm-v1              # CPU runtime (omit --gpu/--tpu)
docker compose exec colab-cli colab exec -s tiny-lstm-v1 \
    -f /notebooks/tiny-lstm-v1.ipynb --timeout 3600                  # default timeout is 30s -- raise it
docker compose exec colab-cli colab download -s tiny-lstm-v1 /content/best.pt /notebooks/tiny-lstm-v1_best.pt
docker compose exec colab-cli colab download -s tiny-lstm-v1 /content/metrics.json /notebooks/tiny-lstm-v1_metrics.json
docker compose exec colab-cli colab stop -s tiny-lstm-v1
```

**`colab download`'s remote path must be `/content/...` (or `content/...`) even for a file the
notebook wrote with a bare relative name** — confirmed live: a notebook's cwd is `/content` (so
`torch.save(model, "best.pt")` lands at `/content/best.pt`, and `colab ls` — whose own path
argument defaults to `"content"` — shows it fine), but `colab download -s x best.pt out` still
fails with `File or directory not found: best.pt`. Unlike `colab ls`, `colab download` does not
default a bare relative path against `/content` itself. `model/colab_runner.py`'s `download()`
normalizes this automatically; a manual `colab download` invocation must do it by hand.

`colab exec` appears to block until the notebook finishes (the bundled examples download output
immediately after it returns) — so its exit code is the completion signal, and there's no
separate "poll for done" step needed if you're willing to hold that terminal. To watch progress
**while** it's running instead, run `colab status -s tiny-lstm-v1` / `colab log -s tiny-lstm-v1`
from a second `docker compose exec`.

**Confirmed live: `colab log`'s default (non-`-o`) view and its `.txt` export both show only the
*code* of each executed cell, not its printed output or return value.** So it is not a way to
watch a notebook's own `print(f"epoch {epoch}/... train=... val=...")` progress lines —
`colab exec`'s own captured stdout (see `model/colab_trainer.py`, which logs it unconditionally)
is the only place those actually appear today. Whether some other `colab log` invocation surfaces
per-cell stdout is still unconfirmed; what's confirmed is that the plain and `.txt`-exported
forms don't.

Then register the downloaded run with algoforge:

```
python -m scripts.import_training_run --model-id <ID> --dataset-id <ID> \
    --checkpoint tiny-lstm-v1_best.pt --metadata tiny-lstm-v1_metrics.json
```
(from `algoforge/backend`, outside this container — see that script's own docstring.)

## Known unknowns (flag before relying on this for anything unattended)

- Whether `colab exec`'s exit code reliably reflects a training error *inside* the notebook
  (e.g. the sha256 assertion failing) vs. only CLI/connection-level failures — untested.
- Whether `colab log` shows live progress from a still-running execution or only a completed
  one's output — untested.
- Whether Colab session quota/compute is billed against the authenticated Google account the
  same as opening colab.research.google.com manually (expected: yes, unconfirmed).
- Whether a Colab runtime provisioned this way times out/disconnects the same as the browser UI
  when idle — the CLI advertises an "automatic keep-alive daemon" against this, unverified here.
- The CLI's own `--help` reports `--auth` defaults to `oauth2`; its bundled `colab readme` text
  says the default is `adc`. Deferred to the live behavior actually observed in this environment
  (unauthenticated commands trigger an oauth2 browser flow), documented above as ground truth.
