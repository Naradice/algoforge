# Jev replication experiment

Investigates whether TypeSafe's ["Jev" model](https://docs.typesafe.ai/introduction) — a
non-Transformer (architecture undisclosed) "System One model" that answers typed, parallel
questions against a shared state with calibrated probabilities instead of generating text — can
be functionally reproduced with known architectures (starting with BERT), and if not, which of
Jev's observable properties is the one a standard architecture can't reach. Runs as a new
architecture family in `model_core` (`architectures`/`trainers`), alongside the existing
financial-time-series family (LSTM/GAN/VAE/AR) — same TrainingRun/MCP/hyperparameter-search
infra, unrelated dataset/task domain. Training data is synthetic, generated by an LLM (no access
to Jev's own training data or weights — only its public API contract). Runs on this project's own
GPU compute, not the Colab CPU pipeline (`docs/colab-workflow.md`) built for tiny financial
models — these models and datasets don't fit that pipeline's assumptions.

Built to be driven autonomously by study_manager (its own agent loop, not manual API calls) —
that end-to-end loop, submitting this investigation as a real research question and letting
BRIEFING → approval → Agent Loop run it via AlgoForge's MCP, is itself the point of this
investigation being done this way at all (see study_manager's own README). The engineering below
only builds the primitives study_manager's `collect`/`train`/Evaluate decisions need to exist
first — it does not itself drive any experiment loop.

Phase plan (Phase 0 fixes the spec below; Phase 1 builds the first BERT baseline; later phases
scale question count, make questions dynamic, scale state length — swapping in a long-context
encoder where plain BERT's 512-token limit makes that impossible — add state-update/iterative
decision loops, compare against GPT/recurrent baselines, and finally isolate architecture
contribution from RLCD-style training-objective contribution). Each phase's own doc section is
added as that phase starts.

## Phase 0 — Jev's observable spec, fixed

Extracted 2026-09-18 from `docs.typesafe.ai` (`/introduction`, `/primitives`, `/primitives/advanced`,
`/confidence`, `/concepts/state`, `/concepts/system-one`, `/introduction/machine-learning-primer`,
`/patterns/fan-out`). This is Jev's *public API contract* — nothing here is an architecture claim;
see "What's deliberately NOT specified" below for what the docs explicitly withhold.

### The three primitives

| Type | Input (`type`, `instructions`, `criteria`) | Output | Notes |
|---|---|---|---|
| **Choice** | `criteria`: **map** of option → description (plain string or a JSON rubric — see Advanced Structure below) | `choice` (selected key), `probabilities` (dist. over all option keys), `confidence` | Not a fixed label list — each option carries its own (possibly rich) description every time |
| **Score** | `criteria`: **ordered list** of level descriptions | `score` (continuous position, **may fall between levels**), `legend` (position→description map), `probabilities` (dist. over levels), `confidence` | Score is a continuous value derived from a distribution over discrete levels, not a plain scalar regression target |
| **Noul** | `criteria`: optional, clarifies what "true"/"false" mean | `noul`: **single float, 0–1** | This is a probability of affirmative, not a binary label — 0.5 means genuinely uncertain, not "false". **Model as a calibrated probability output (BCE-style), not binary classification.** |

`instructions` on all three types is a natural-language judgment prompt that may reference state
fields with backtick dot-bracket paths, e.g. `` `ticket.messages[0].text` `` — the model is
expected to resolve a path reference against the actual state content, not just read it as
literal text. **This is a distinct capability worth testing explicitly in Phase 3/4** (dynamic
questions): does a path reference resolve correctly, separately from whether free-form language
pointing at the same content does.

**Advanced Structure** (`/primitives/advanced`): `instructions`, Choice's per-option descriptions,
Score's per-level descriptions, and Noul's `criteria.true`/`criteria.false` all accept
`string | object | array | null`, not just plain strings — e.g. a Choice option can carry a JSON
rubric (`what` / `not_for` / `examples` keys) or a nested taxonomy subtree. Phase 3/4's "dynamic
question" generator should include this — a fixed-label classification head cannot represent an
option set that changes shape (not just content) per question.

### `confidence` is derived, not a separate learned output

"The answer's `confidence` property collapses that [probability distribution's] shape into a
single number from 0 to 1" — a flatter distribution (no clear winner) means lower confidence.
**Implication for Model A (Phase 1): don't train a separate confidence head.** Compute it as a
post-hoc function of the Choice/Score probability distribution (e.g. max probability, or a
normalized negative-entropy) and evaluate whether *that derived value* behaves the way Jev's own
guidance assumes (e.g. correlates with correctness) — that correlation itself is a property to
test, not something to bake in by construction.

No calibration guarantee is claimed for confidence specifically — docs explicitly tell developers
to "start with conservative thresholds, test with your own data" rather than trusting a
pre-established calibration property. The *probabilities* underlying Choice/Score/Noul are where
the calibration claim actually lives (see below) — confidence is just a convenience summary of them.

### State

Three accepted shapes: plain string, JSON object (recommended for most requests — "each part of
the state has a descriptive name and its relationships remain clear"), or JSON array (e.g. a
message thread). Text only — no images/audio/video ("not supported (yet)"). **One request
evaluates one state against one-or-more questions; all questions see the identical state and are
evaluated independently.**

**Token budget: ~32,000 tokens (~150,000 English characters), shared between state and questions
combined** — not a separate budget per side. This directly bounds Phase 2's scaling sweep: N
questions growing large enough to approach this shared budget is Jev exceeding its own declared
operating envelope, not just an implementation limit of whatever architecture is standing in for
it. Worth treating the sweep in two parts — up to the shared-budget ceiling (testing whether a
stand-in architecture matches Jev's claimed behavior *within its own claimed envelope*) and, if
wanted, deliberately beyond it (testing where the stand-in architecture itself falls over, which
is a different question with a different interpretation).

### The one concrete, falsifiable performance claim

From "Speculative Fan-Out" (`/patterns/fan-out`): *"All questions are evaluated in parallel, so
adding more questions to a call typically doesn't add any latency to the response."* No numbers
are given (no max batch size, no actual latency figures, no benchmark) — this is the strongest
plain-language claim in the whole doc set, and it's exactly Phase 2's target: does *any*
candidate architecture (starting with plain BERT, where sequence length — and therefore compute —
necessarily grows with N) actually deliver ~flat latency in N, or does replicating this specific
property require something other than "put N questions in one sequence and run self-attention
over all of it"?

### Training objective (RLCD) — relevant to Phase 9, not earlier phases

Jev is trained with **RLCD — "Reinforcement Learning for Calibrated Decisions"** (the doc's own
term, not the user's invented shorthand), explicitly *not* RLHF: "RLHF trains models to produce
responses that humans prefer" via preference optimization, which causes "mode dropping" and
"an output can be compelling to a person without being reliable enough for unattended
automation." RLCD instead "trains \[Jev\] to return decisions and calibrated probabilities
instead of generated text," with calibration defined precisely: *"Outcomes assigned a probability
of 0.2 should occur about 20% of the time. Outcomes assigned a probability of 0.8 should occur
about 80% of the time."* This is the standard reliability-diagram definition of calibration — so
ECE/Brier/reliability-diagram evaluation (already planned for Phase 1) is measuring exactly the
property Jev's own training objective targets, not a proxy for it. Phase 9 isolates how much of
Jev-like calibration is architecture vs. this training objective by comparing standard CE against
an RLCD-style objective (reward = calibration quality, e.g. negative Brier/NLL, rather than
preference) on the *same* architecture.

### What's deliberately NOT specified (confirms Phase 0's own premise)

No mention anywhere of Transformer/attention/standard NN components, autoregressive generation,
parallelism mechanism, or training methodology beyond the RLCD framing above. The docs
acknowledge this gap only obliquely ("Read the \[machine-learning\] primer to learn how System
One models work" — which turned out to cover training objective, not architecture). **This
confirms the plan's own premise is well-founded: internal architecture genuinely isn't assumed by
anything public, so Phase 1 onward is free to treat it as the open question it is.**

## Phase 1 — Model A (BERT + fixed heads): primitives built, not yet run as a study_manager investigation

Built so far (engineering only — see "Status" for what's actually been exercised):

- **`data/collectors/llm_typed_decisions.py`** — new `datasource.type="llm_typed_decisions"`,
  dispatched from `celery_worker._run_collector` exactly like every other collector. Generates
  synthetic (state, questions, gold answers) examples via algoforge's existing Gemini wiring
  (`GOOGLE_API_KEY`/`google-genai` — reused rather than adding a second LLM provider/credential
  just for this), for a **fixed** three-question set mirroring TypeSafe's own worked example
  (a support-ticket triage: `refund_requested` noul, `urgency` score, `category` choice). Output
  is JSONL, one line per example, in TypeSafe's own request/response shape (questions/answers
  keyed by id) — already the shape Phase 3/4's dynamic per-example questions will need, even
  though every example here uses the same fixed three.
- **`model_core/architectures/jev_bert.py`** (`JevBertModel`) — a pretrained BERT encoder plus
  one head per question, each head reading the hidden state at that question's own `[Q_<id>]`
  marker token (a real added vocabulary token, not [CLS]) — the "special token" design
  (this doc's own plan calls it "B1"), so the "parallel decisions in one shared-state sequence"
  property is actually exercised, not just a multi-head classifier standing in for it. **Not**
  wired into `architectures.build_model()`'s generic dispatch — raises there, directing to this
  module directly — for the same reason ARIMA isn't: nothing about `build_model`'s
  financial-architecture kwargs (obs_len/pred_len/feature_cols/a single criterion) applies here.
- **`model_core/trainers/typed_decision.py`** — `TypedDecisionDataset` (tokenizes state +
  fixed questions into one sequence, tracks each marker token's position, fixed-question-set
  only), the combined BCE+CE multi-head loss, `score_from_logits` (Score's continuous position =
  the softmax-probability-weighted expectation over level indices, per this doc's Phase 0 spec),
  and `compute_calibration_metrics` (ECE + Brier score per question, using the binned/top-label
  definitions matching Jev's own RLCD calibration definition — see Phase 0's spec above).
- **`celery_worker._run_typed_decision_training`** — the training loop itself (plain AdamW, no
  scheduler/warmup/early-stop machinery, unlike `_train_model`'s — this shape doesn't need any
  of that), dispatched from `_train_model` via `TYPED_DECISION_ARCHITECTURES` exactly like
  `ARIMA_ARCHITECTURES` dispatches to `_run_arima_training`. Writes a `ModelValidation` row
  itself at the end with the calibration report (`get_model_validations`/`compare_model_runs`
  already surface this to study_manager's Evaluate step — no new MCP tool needed) — unlike every
  other architecture, where that's normally a separate human/MCP-triggered step, because
  calibration is this investigation's actual question, not an optional afterthought.
- `model_core/pyproject.toml` gained an optional `jev` extra (`transformers`) rather than a hard
  dependency, since this path doesn't run via the Colab pipeline that package also serves.

**Known limitation, not yet addressed:** the "ground truth" for this entire investigation is
itself an LLM's judgment (the collector's labeling model), not Jev's. A trained Model A can only
ever be evaluated against how well it reproduces the *labeling LLM's* typed decisions — that's a
real ceiling on this investigation's external validity, not a bug in the collector (see that
module's own docstring).
