# F1 後続 P3 の前提監査: DDM の初期化・状態更新・予測生成

目的: burn-in 感度分析(P3)を計画する前に、F1 の DDM 予測がどのように作られ、どの介入が可能で、何が変わるのかを実装から確認する。実験ではない(実現値も評価も使わない)。対象コード: `backend/research/f1_ddm.py`、`backend/data/collectors/ddm_simulator.py`(`DDMv3`)。計測の補助スクリプト: `backend/research/p3_burnin/audit_measure.py`(結果: 同ディレクトリの `audit_measure_results.json`。12 パス、候補 1 つ(delta = 0、wma = 7)、実データなし)。F1・P2 の既存結果は変更していない。

## 1. 予測生成の流れ(事実)
1. 原点(ブロックの最後の行)ごとに、直前 60 本の ATR からバケット(推定期間の ATR の 20 分位)を決める。**予測が原点に依存するのは、このバケットだけ**。
2. バケットごとに、推定期間の窓(最大 300 窓、seed 20261117)の実統計から、候補 (delta, wma) の集合(上位 8)が固定されている(`ddm_mapping.json`)。
3. 各バケットで 1,000 本のパスを生成する。パス k の seed は `8,000,000 + seed_id·1,000,000 + q·20,000 + attempt`、候補は `attempt` の順に巡回する。失敗したパス(例外、非有限、価格 ≤ 0)は捨てて次の attempt に進む。
4. 1 本のパス: `random.seed`、`np.random.seed` を設定し、`DDMv3(num_agent=300, …, §11 の減衰ショック)` を**新規に構築**して `n_trades = (60·24 + 1)·20` 回の約定をシミュレートする。20 約定 = 1 本のローソク足で、その最後の約定価格が終値。ホライズン h の予測値は `log(closes[60h] / closes[0])`。
5. **実際の市場の履歴(価格、直近リターン、状態)は予測に一切入らない**。保存済みアンサンブルはバケットごとの無条件のパス分布であり、状態更新(データ同化)の仕組みは存在しない。したがって、F1 の評価は「未来情報の混入」の余地がない(バケットの ATR は原点までの情報、写像は推定期間のみ)。

## 2. 初期状態(各パスで毎回、乱数から新規に作られる)
| 状態 | 初期化(`DDMv3`/`_DDMv1.__init__`) | 備考 |
|---|---|---|
| ポジション | 買い 150・売り 150 に均等分割して並べ替え | 50/50 は過去の発散の教訓(記憶) |
| エージェント価格 | `U[P0, P0 + spread]`(P0 = 100、spread = 1) | 価格レベルは 100 基準で、実際の USDJPY の水準とは無関係 |
| 傾向 `tend` | `U[0.01, 0.02]` を丸め | |
| `dealer_sensitive` | `U[−3.5 + delta, −1.5 + delta]` | |
| WMA の重み | `U[0, 1]` の wma 個 | |
| `market_price`、`price_history` | `P0 + spread` の 1 点のみ | **WMA の追従項は `price_history` が wma + 1 点たまるまで 0**(初期の数約定は追従項なし) |
| `_step_count`(ショックの時計) | 0 | 約定の有無によらず 1 ステップごとに +1 |
| スプレッドのフィードバック、強制清算 | 無効(`spread_feedback_a=None`、`loss_limit=None`) | |
- 初期状態は「固定した 1 つの状態」ではなく、**毎パスで乱数から引かれる**。したがって、既存のアンサンブルは初期状態の乱数について周辺化されているが、**「パスの開始直後」という時間的な位置は常に同じ**(エージェントの価格・ポジションが未緩和の状態から始まる)。

## 3. §11 の減衰ショックは「パス開始からの経過ステップ」の関数
- ショック確率は `p(t) = 0.002 · exp(−t/300)`(t = 経過ステップ、床 0)。1 約定あたり平均 1.45 ステップ(実測 1.4509)なので、τ = 300 ステップ ≈ 207 約定 ≈ **10 本のローソク足**。
- 1 パスあたりの期待ショック数は 0.002 × 300 = 0.6(12 パスの実測 0.67)。**ほとんどが最初の約 20 本のローソク足の間に発生**する。ショックの発生を独立な近似ポアソン過程とみなすと、少なくとも 1 回起きるパスの割合は 1 − e^(−0.6) ≈ 45%(期待回数 0.6 と発生確率 45% は別の量。12 パスの実測は 8 パスで 1 回以上 = 67% だが、標本が小さく近似と矛盾しない)。まれな早期イベントで、約半数のパスではまったく起きない。
- **この数値の訂正**: 本監査文書の初版(コミット 3f73e4b)は「約 6 割のパスで 1 回」と記述していたが、期待回数と発生確率を混同していた。
- したがって、**§11 のショックと「初期の過渡状態」は時間的に重なっている**。パスの先頭を捨てる単純な burn-in(ショックの時計がそのまま進む)は、ショックを同時に取り除く(期待ショック数の残り: 15 本捨てると 0.14、60 本で 0.002、240 本で ~0)。初期状態の効果と、ショックの効果を区別するには、ショックの時計の扱いを独立に操作する必要がある。
- 実測(12 パス、1 候補): 最初の 5 本のローソク足の平均絶対リターンは、終盤(360〜1440 本)の 1.25 倍、それ以降は 0.96〜1.09 倍。初期の過渡的な変動は小さく、ショック発生の有無に依存する可能性が高い(1 候補のみの測定で、一般化しない)。

## 4. 可能な介入と、各介入で変わるもの
| 介入 | 実装 | 変わるもの | 備考 |
|---|---|---|---|
| I1: 先頭 B 本を捨てる(ショックの時計は進む) | 同じ seed でより長いパスを生成し、`closes[B : B + 1441]` を使う | 同じパスの後ろの窓。**先頭部分は C0 と同一(同じ乱数列)**なので、対応比較ができる。ショックはほぼ消える | シミュレータの改修は不要 |
| I2: B 本捨てた後でショックの時計を 0 に戻す | `simulate(n_trades=B·20)` の後、`model._step_count = 0` を設定して続きを生成 | エージェント状態は緩和済みで、ショックの時間構造は C0 と同じ | 外部からの属性設定のみ(シミュレータのコードは変更しない)。B 本の先頭は C0 と同一で、後半は乱数列が分岐 |
| I3: ショックなし | `exogenous_shock_probability = 0` | ショックの効果のみ(ショックの乱数消費がなくなるため、乱数列は C0 と分岐) | 「ショックを除く」対照 |
| 実観測を状態に入力する方式 | **対応する仕組みなし** | – | `DDMv3` に外部の価格を入れる口がなく、エージェントの状態(ポジション、価格)は観測できない。`price_history` に実価格を入れても、WMA の追従項にしか効かず、価格レベル(100 基準)の問題がある。モデル改修を伴うため **P3 の範囲外**(別計画) |

## 5. 時間単位と長さの目安
- 時間単位: 約定(`n_trades`)。20 約定 = 1 ローソク足、1 約定 ≈ 1.45 ステップ。burn-in の長さは、ローソク足の本数で表す(1 本 = 20 約定 = 約 29 ステップ)。
- 時定数: ショックの τ ≈ 10 本。WMA の窓は最大 wma 約定(候補の wma ≤ 数十。1 本未満)。エージェント価格が定常的な分布に緩和する時間は、このコードからは解析的に読み取れない(実測が必要で、P3 の中の確認項目にする)。
- 計算量: パス長が B 本増える分だけ増える(B = 240 で +17%)。F1 の 1 seed(20 バケット × 1,000 パス、18 ワーカー)は約 1.5 時間かかった(マニフェストの記録)。

## 6. P3 計画への含意
1. **主な混同**: 初期状態の過渡と §11 のショック(時間的に重なる)。条件に「ショックの時計を操作する」軸が必須(I1 対 I2、I3)。
2. 同じ seed の C0 と I1 は、先頭が同一のパスなので、対応比較の精度が高い(同じ初期状態、同じ乱数列)。I2、I3 は先頭以降で乱数列が分岐するため、アンサンブルとしての比較(原点ごとの CRPS の差)になる。
3. 実観測を入力する方式は含めない。含めるなら、未来情報の混入を防ぐ別のゲートと、モデル改修の計画が必要。
4. 失敗パス(`None`)の割合が条件によって変わると、条件間でパスの母集団が変わる。条件ごとに成功率を記録し、報告する。
5. F1 の既存アンサンブル(C0)は、バイト単位で再現できるはず(同じ seed と同じコード)。P3 の最初のゲートにする。

## 7. 乱数の消費(v0.2 で追加)
- `DDMv3` はすべての乱数(時間ノイズ `random.choices`、ショックの発生判定 `random.random()`、ショックの方向 `random.random()`)を同じグローバルな `random` モジュールから引く。**ショックが有効なときは毎ステップ 1 回、ショックの判定のために乱数を消費し**(発生時はさらに 1 回)、確率 0 のときは**乱数を消費しない**(`_maybe_exogenous_shock` の先頭で `None` を返す)。
- このため、ショックの有無(C0 対 C3、C1 対 C5 など)を変えると、**最初のステップから通常の状態更新の乱数列がずれる**。初期状態(コンストラクタで引かれる)は同じだが、その後のパスは分岐し、パス単位の対応比較にならない。
- 変更範囲の監査: ショック用の乱数だけを独立な `random.Random(shock_seed)` から引くには、`_maybe_exogenous_shock` の 2 行(`random.random()` の 2 か所)の置き換えが必要。シミュレータのソースを変更せず、P3 側のサブクラスで `_maybe_exogenous_shock` だけをオーバーライドすれば実現でき、F1 の既存コードパス(`DDMv3`)は変わらない。サブクラスの「従来モード」(グローバルな `random` を使う)が `DDMv3` とバイト単位で一致すること、を再現性ゲートにする(P3 計画 v0.2)。
- 毎ステップで、ショックの判定用と方向用の 2 つの乱数を**常に**引く(確率が 0 でも、発生しなくても)設計にすれば、ショックの有無・時計の扱いを変えても、通常の状態更新の乱数列は完全に共通になる(共通乱数)。
